# 需求

## 权威范围

本文是 `dsh-codexpro` 的需求基线，唯一拥有目标、用户、场景、功能范围、非目标、约束与验收语义。技术选型归 `技术栈设计.md`，模块与目录组织归 `项目结构设计.md`，机制细节归 `technical-details/`。

## 一、背景与问题

CodexPro 是一个本地 MCP server，让具备自定义 MCP 权限的 ChatGPT 会话获得对指定本地仓库的读写、搜索、编辑与受控命令执行能力。它的配置按「工作区根目录」组织：每个目录一份 profile 文件，`.ai-bridge` 计划与 `AGENTS.md` 都在该目录下落地。

在 DSH 上使用它有一组重复劳动，且每次换项目都要重来：

1. 配置按目录绑定，新项目要进入该目录重跑一次交互式向导；
2. 授权哪个目录、开哪些能力写在 codexpro 自己的 profile 里，与 DSH 的工作区清单是两份互不知情的账；
3. 进程要在终端手工启动并保持前台运行，终端一关就断；
4. 授权目录一旦失去隔离，个人资料目录也会被一并暴露给 ChatGPT。

DSH 已经维护了一份权威的工作区清单（`ctx.workspaceRegistry`），但这份清单没有流向 codexpro。

## 二、目标与用户

**目标**：把 codexpro 的配置与进程生命周期收进 DSH 设置页，使「在 DSH 里打开过的项目」成为唯一的授权来源，日常使用不再需要手工维护 codexpro 配置。

**用户**：使用 DSH，且已具备可调用自定义 MCP 连接器的 ChatGPT 账号的使用者。

**核心场景**：

1. 首次配置：在设置页勾选要授权的 DSH 工作区，选定 tunnel 方式与端口，点击启动。
2. 日常使用：打开 DSH，进入设置页确认状态为运行中，复制 Server URL 填入 ChatGPT 连接器，之后在 ChatGPT 侧用 `open_workspace` 切换项目。
3. 新增项目：在 DSH 里打开一次该项目使其进入工作区清单，回到设置页勾选，配置自动同步。
4. 收工：在设置页点击停止，或直接关闭 DSH 实例。

**期望结果**：配置面（哪些项目被授权、以什么能力暴露）在 DSH 内单一可维护；进程启停有明确的状态反馈；不产生需要手工善后的残留进程。

## 三、功能范围

| ID | 功能需求 |
|----|----------|
| R-01 | 设置页列出当前 DSH 实例的工作区清单，每个工作区一个可勾选项，勾选状态即授权意图 |
| R-02 | 勾选变更后，codexpro 的 profile 文件按当前授权集自动写入，无需用户在终端执行任何命令 |
| R-03 | 设置页提供进程启停控制，并实时呈现进程状态（未运行 / 启动中 / 运行中 / 启动失败 / 已停止） |
| R-04 | 进程运行中时呈现可复制的 Server URL，供填入 ChatGPT 连接器 |
| R-05 | 设置页可选择 tunnel 方式，首次配置默认取 `none`（仅本地、不产生公网入口） |
| R-06 | 设置页可配置本地端口 |
| R-07 | 设置页可配置 bash 执行模式（`off` / `safe` / `full`）与写入模式（`off` / `handoff` / `workspace`） |
| R-08 | 进程运行中时呈现健康状态，来源为 codexpro 自身的健康端点 |

## 四、非目标

- 不实现 codexpro 本身，不代理、不修改其行为；本插件只做配置投影与进程生命周期管理。
- 不提供任何模型可见工具（无 `defineTool`）；全部能力经设置页由人操作。
- 不支持 `handoff` 与 `pro` 模式；本插件面向 `agent` 模式（ChatGPT 直接读写工作区）。
- 不管理 ChatGPT 侧连接器；Server URL 只提供复制，连接器创建由用户手工完成。
- 不做多实例共享同一份 codexpro 配置（见 C-05）。
- 不支持在授权集之外临时开放单个目录（无「本次会话额外授权」通道）。
- 不自动启动进程；启动是显式的人工动作（见 C-04）。

## 五、约束

| ID | 约束 | 来源 |
|----|------|------|
| C-01 | 不提供模型可见工具；插件不注册 `ctx.tools` | 用户裁决 |
| C-02 | 插件单向写 codexpro 配置：插件是配置唯一事实源，codexpro 侧的手工改动会在下次同步时被覆盖 | 用户裁决 |
| C-03 | 授权候选集只来自 DSH 工作区注册表，不提供手工输入任意路径的入口 | 用户裁决 |
| C-04 | 进程跟随 DSH 实例生命周期：不脱离父进程常驻，DSH 实例结束即随之终止 | 用户裁决 |
| C-05 | 每个 DSH 实例使用独立的 codexpro 数据目录（`CODEXPRO_HOME` 置于该实例 `$DSH_HOME` 下），不共用默认 `~/.codexpro` | 用户裁决 + 仓库实例隔离原则 |
| C-06 | 进程启动参数满足 codexpro 的 `agent` 模式语义：`mode=agent`，`write` 取值限于 `off` / `handoff` / `workspace` | codexpro 行为 |
| C-07 | HTTP token 在多次启停之间保持稳定，避免 ChatGPT 连接器因 token 变化而失效 | 需求 R-04 |
| C-08 | 实现以 Windows 为首要目标平台，但平台相关行为（路径、进程终止、shell）必须经抽象隔离，不得散落硬编码 | 用户裁决 |
| C-09 | 未在 DSH 工作区清单中的目录不得被写入 codexpro 授权集；目录不存在时不得写入（codexpro 对不存在的授权根直接拒绝启动） | codexpro 行为 + C-03 |
| C-10 | 不向 codexpro 授权集写入个人资料类目录的默认值；勾选状态初始为空 | 用户裁决 |

## 六、验收条件

| ID | 验收条件（可观察） |
|----|--------------------|
| AC-01 | 在插件页本行的配置页勾选 N 个工作区并点「保存」后，目标 codexpro profile 文件的 `allowedRoots` 恰为这 N 个目录的 realpath 归一结果，无多余项、无遗漏 |
| AC-02 | 取消全部勾选并保存后，profile 的 `allowedRoots` 为空或缺少该键，且不含任何先前授权项 |
| AC-03 | 点击启动后，进程状态依次呈现启动中与运行中；运行中状态下 `GET /healthz`（带 token）返回 `ok: true` |
| AC-04 | 运行中状态下呈现的 Server URL 可被 ChatGPT 连接器成功建连（人工在浏览器验证，属页面级走查） |
| AC-05 | 点击停止后，状态回到未运行，本地端口恢复可绑定，且无遗留的子进程（codexpro server 进程与 tunnel 进程均不存在） |
| AC-06 | 关闭 DSH 实例后，无遗留的 codexpro 相关进程（含 tunnel） |
| AC-07 | 连续两次「启动 → 停止 → 启动」后，Server URL 中的 token 部分保持不变 |
| AC-08 | `default tunnel` 为 `none` 时，进程启动不产生任何公网监听或对外 URL |
| AC-09 | 插件在 `--dump-config` 中呈现为单一行且来源正确；实例启动无 `N entries did not activate`、无 `N required plugin[s] did not activate` |
| AC-10 | UI 走查：侧栏插件页本行出现「配置」控件，打开后无 DevTools Console 报错（无 `slot entry crashed`） |

**验收作弊姿势排除**：

- AC-01 / AC-02 的判据是**写入后读回文件内容**，不是「代码里调用了写函数」；断言必须读取 profile 文件的实际 JSON，不得以 mock 调用次数代替。
- AC-05 / AC-06 的判据是**操作系统层面的进程存在性**，不是「已调用终止方法」；必须枚举实际进程或校验端口与健康端点均不可达。
- AC-03 的判据是 codexpro 自身健康端点返回，不是「进程句柄未结算」。
- AC-07 必须在**同一实例的两次真实启动**之间比对，不得以「代码里复用了同一个 token 变量」代替。
- AC-09 必须以实例启动日志为准，不得以「配置文件看起来对」代替。

## 七、未决与缺证

以下事项影响验收语义的成立，登记于 `TODO.md`。

- 待确认：**非 Windows 平台的行为**。全部取证在 Windows 上完成；C-08 要求实现按可移植标准编写，但**不支持任何未经实测的平台声明**。AC-05、AC-06 的「无遗留子进程」在其他平台未取证。

- 待确认：**`anchorDir` 是否需要用户可配**。当前视为部署事实（非 volatile），不出现在设置页。
