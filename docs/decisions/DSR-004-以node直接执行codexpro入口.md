# DSR-004：以 node 直接执行 codexpro 入口，不走裸名

> **决定**：`argv` 形态固定为 `[process.execPath, <codexpro 的 CLI 入口 .mjs 绝对路径>, "start", ...]`，不使用裸名 `codexpro`。
> **理由**：Windows 上裸名解析到 `.cmd` shim，在 argv 不经 shell 解释的语义下直接 `ENOENT`（已实测）。
> **被否决项**：裸名 + `shell: true`；显式解析并执行 `.cmd`；要求用户手工配置可执行路径。

## 上下文

`ctx.subprocess.spawn` 的契约明确：`argv` 是「可执行文件与参数」，**绝不经 shell 解释**。这一点是安全特性而非限制——它消除了参数注入面。

而 codexpro 在 Windows 上安装后的入口是 npm 生成的批处理 shim（`codexpro.cmd`），其内容以 `cmd.exe` 语义转调 `node <...>/scripts/codexpro.mjs`。

实测结果：

| 形态 | `shell: false` 结果 |
|------|---------------------|
| `['codexpro', '--version']` | `ENOENT` |
| `[process.execPath, '<...>/scripts/codexpro.mjs', '--version']` | 成功，输出 `0.30.2` |

## 真实方向及评价

| 方向 | 可行性 | 安全面 | 代价 |
|------|--------|--------|------|
| `node` + `.mjs` 入口绝对路径 | 已实测可行 | 无 shell 解释，无参数注入 | 需经包解析定位入口，不能硬编码 |
| 裸名 + `shell: true` | 可运行 | **打开 shell 解释面**：参数经 cmd 解析，路径含空格或特殊字符时行为不可控，且构成注入面 | 与 seam 的安全取向相悖 |
| 显式解析 `.cmd` 并调用 | 可行但无必要 | 仍需 cmd 语义执行 | 多一层平台特化，且 `spawn` 对 `.cmd` 仍要求 shell |
| 要求用户配置可执行路径 | 可行 | 无 | 把安装细节推给用户，违背「无需操心」的目标 |

## 最终决定与理由

取**方案一**。

理由：它是唯一既实测可行、又不引入 shell 解释面的形态。方案二的代价（注入面 + 行为不可控）与本插件处理「用户项目路径」的场景直接冲突——路径中带空格或括号在 Windows 上很常见，把这类路径交给 cmd 解释是不可接受的。

入口路径通过 `createRequire` 解析 `codexpro/package.json` 得到，取其 `bin` 指向的真实 `.mjs` 文件，**不硬编码绝对路径**（用户的 Node 全局目录位置因人而异）。解析失败时给出稳定错误码与可读原因（codexpro 未安装、包结构变化），**不回落到裸名**——静默回落到一个已知会失败的形态，只会把一个清晰的错误变成难查的 ENOENT。

## 直接后果

- 不依赖 PATH 中的 `codexpro` shim。
- 参数中的路径（锚点、工作区）不经 shell，含空格与特殊字符均安全。
- 该逻辑是本插件**唯一允许出现平台相关分支**的位置（与 C-08 一致），须附注释说明依据。
- 若 codexpro 未来改变包结构（`bin` 指向变化），解析逻辑需随之调整；已通过「解析失败即明确报错」使这类变化可诊断。

## 重访条件

- codexpro 提供无 shim 依赖的调用形态（如直接暴露 `.mjs` 入口且路径稳定）。
- 目标是 POSIX 平台且实测证明裸名可用（此时仍需保留 Windows 分支）。
