# DSR-002：进程跟随 DSH 实例生命周期

> **决定**：codexpro 进程由 `ctx.subprocess` 托管，随插件 fiber 与 DSH 实例终止，**不脱离父进程常驻**。
> **理由**：宿主托管是唯一能同时覆盖「插件卸载」与「DSH 进程退出」的清理路径，且提供 Windows 整树终止；避免孤儿 server 与 tunnel。
> **被否决项**：detached 独立常驻；跟随 DSH + 持久化期望运行状态自动恢复。

## 上下文

codexpro 是长驻 CLI：`start` 会拉起 `dist/http.js` server 子进程，并自行 spawn 一个 tunnel 子进程（cloudflared / ngrok / tailscale），然后阻塞等待。

调研中的关键证据：**Windows 上外部发送 `SIGTERM`/`SIGINT` 不执行目标进程的 JS 处理器**（实测：目标进程注册处理器并在其中写标记文件；外部发信号后进程消失而标记文件未生成）。这意味着若以外部信号终止 codexpro，其 `cleanup()` 不会运行，server 与 tunnel 会成为孤儿并继续占用端口与公网隧道。

## 真实方向及评价

| 方向 | 清理覆盖 | 常驻性 | 代价 |
|------|----------|--------|------|
| `ctx.subprocess` 托管，跟随 DSH | 插件卸载 + DSH 退出（服务销毁承诺终止并等待全部托管进程）；Windows 经进程容器整树 | DSH 关闭即停 | DSH 重启后需重新启动；需实测整树能力是否激活 |
| detached 独立常驻 | 无；须自建孤儿认领与防重复启动 | 关 DSH 后继续跑 | 与实测结论直接冲突：硬杀父进程会留下孤儿；需处理「插件无句柄但进程活着」的复杂状态 |
| 托管 + 持久化「期望运行状态」，DSH 启动后自动恢复 | 同方案一 | 近似常驻（有间断） | 多一层状态记忆；自动恢复与「启动是显式人工动作」的定位冲突 |

## 最终决定与理由

取**托管**（方案一）。

理由有三：

1. **清理覆盖是决定性的**。方案二在实测证据下必然产生孤儿，而孤儿表现为端口被占与公网隧道残留，恰是用户不能自行诊断的一类故障。
2. **服务契约明确承诺**：「服务销毁会终止所有仍在运行的托管进程并等待其退出」。这是宿主提供的保证，优于自建。
3. 方案三的自动恢复与需求 R-03（显式启停控制）的取向一致性问题：用户未要求自动启动，且自动重启会在用户不知情时重新打开公网入口——与 S-04（首次默认不暴露）的安全取向相悖。

## 直接后果

- DSH 实例关闭 ⇒ codexpro 及其 tunnel 一并终止（AC-06）。
- DSH 实例重启后需在设置页重新点击启动（已知取舍，接受）。
- 显式停止走 stdin `q` 主路径，`handle.terminate()` + `waitForExit()` 为兜底（DSR-007）。
- 整树终止依赖 Windows 进程容器；其可用性已实测确认（DSR-008）。
- **不做孤儿认领**：无句柄时杀进程风险高于收益；崩溃残留的 runtime 文件由 codexpro 自行回收。

## 重访条件

- 用户明确要求「关掉 DSH 后 codexpro 继续服务」，且愿意接受孤儿风险与自建认领机制。
- DSH 上游提供跨实例的常驻进程管理能力。
- 实测证明 `ctx.subprocess` 的终止在本机不可靠（此时方案一的核心论据失效）。
