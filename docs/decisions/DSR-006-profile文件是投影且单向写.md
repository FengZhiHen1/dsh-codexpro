# DSR-006：profile 文件是投影，插件单向写

> **决定**：插件是 codexpro 配置的唯一事实源，单向写入 profile 文件；不读回 codexpro 侧的手工改动，不做合并。
> **理由**：双向合并需要一套无歧义解释的冲突规则，而收益仅是保留一处用户本就不该手工维护的配置。
> **被否决项**：插件写为主 + 读回展示差异；双向合并（并集或时间戳新者胜）。

## 上下文

codexpro 的 profile 文件（`profiles/<hash>.json`）可由两条途径修改：

1. 插件依据 DSH 侧的用户意图生成；
2. 用户在终端用 `codexpro setup` / `codexpro settings set` 修改。

两者作用于同一份文件。若不定义规则，会出现「用户在终端改了授权，插件下次同步就把它覆盖掉」这类需要解释的行为。

补充事实：codexpro 的 `settings set` 与 `POST /admin/profile` 都是**写盘待下次启动生效**（其文案明确 «Saved. Restart CodexPro for these profile settings to apply.»），运行中的进程不会热更新配置。

## 真实方向及评价

| 方向 | 语义清晰度 | 用户预期匹配 | 代价 |
|------|------------|--------------|------|
| 插件单向写 | 高：意图唯一来源是设置页 | 高：用户在本插件内看到的就是全部 | 终端侧的手工改动会被覆盖 |
| 写为主 + 读回展示差异 | 中：需定义「差异」的展示与处置语义 | 中：用户看到两套来源，需自行判断以谁为准 | 多一套差异计算与呈现，且不改变覆盖行为——只是把覆盖变得可见 |
| 双向合并 | **低**：并集会让「取消授权」无法表达；时间戳新者胜会让两侧的批量修改互相覆盖 | 低：用户难以预测结果 | 合并规则本身成为需要文档化的新概念；且与安全边界（授权集）耦合，误合并即扩大暴露面 |

## 最终决定与理由

取**单向写**。

关键论据是**授权集是安全边界，不能有歧义**。若采用并集，用户在设置页取消一个授权后，终端侧遗留的记录会把它加回来——安全边界被一个用户看不见的来源恢复，这是不可接受的。若采用时间戳新者胜，则一次批量修改会静默丢弃另一侧的全部意图，同样难以解释。

第二个方向（读回展示差异）不改变覆盖行为，只是增加可见性；而它引入的新概念（什么是「差异」、展示在何处、用户看到差异后能做什么）与收益不成比例。若用户确实需要知道终端侧改过什么，直接查看该文件比在设置页增加一套只读差异视图更直接。

## 直接后果

- 插件的同步是**幂等生成**：由 `Config` 中的意图完全决定 profile 内容，删除 profile 文件可无损重建。
- 终端侧对同一 profile 文件的改动会在下次同步时被覆盖。此行为须在 README 中明示，避免用户困惑。
- 插件不解析 profile 文件的既有内容（除写入前做幂等比对）。
- 因 DSR-003，插件与终端手工使用默认处于**不同数据目录**，冲突场景实际很少发生；本决策主要定义「若发生则以插件为准」。

## 重访条件

- 出现插件无法表达的配置项，且用户确实需要终端侧维护它（此时可改为「插件只写自己拥有的字段，其余保留」，但须明确哪些字段归谁）。
- codexpro 提供配置变更通知或版本化配置，使合并有可靠依据。
