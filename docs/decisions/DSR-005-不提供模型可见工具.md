# DSR-005：不提供模型可见工具

> **决定**：本插件不注册任何 `ctx.tools`，不提供模型可见工具；全部能力经设置页由人操作。
> **理由**：进程启停会改变机器上的公网暴露状态，将其交给模型扩大安全面；而只读状态查询的收益不足以抵消工具描述税。
> **被否决项**：只提供只读状态工具；提供含启停的读写工具。

## 上下文

DSH 插件可以注册模型可见工具（`defineTool`）。对本插件的功能面而言，存在两个可工具化的点：

1. 只读状态查询（进程是否运行、授权了哪些工作区、当前 tunnel 形态）；
2. 进程启停与配置修改。

用户对此的取向是「在设置面板里人工控制进程」，但「不提供任何工具」与「提供只读工具」是两个不同决定，后者不与前者冲突——因此需要一次显式裁决。

## 真实方向及评价

| 方向 | 安全面 | 概念与 token 成本 | 场景价值 |
|------|--------|-------------------|----------|
| 不提供工具 | 最小 | 零 | 状态由人在设置页看 |
| 只读状态工具 | 无直接风险 | 每会话多一个工具描述 | 模型可在作答时提及 codexpro 状态；但「进程是否运行」不影响模型对代码任务的处理 |
| 含启停的读写工具 | **显著扩大**：模型可自行启动进程 ⇒ 在用户不知情时打开公网隧道，并授权本地目录给外部服务 | 多工具描述 + 需处理并发启停 | 用户无需切页面即可启停 |

## 最终决定与理由

取**不提供工具**。

核心论据是风险与收益的不对称：启动进程这一步的副作用是**把本地目录通过公网 URL 暴露给外部服务**，属安全姿态变更而非数据读写。让模型自主触发这类变更，需要用户对「模型可能在你没注意时打开一个持有 token 的公网入口」有明确预期——而用户没有提出这一需求。

只读工具被否决的理由是收益不足：进程运行状态不参与任何代码任务的推理，模型知道与否不改变其行为；而它要为每个会话承担一条工具描述的成本。若将来出现「模型需要知道 codexpro 状态才能正确作答」的具体场景，可单独重访。

## 直接后果

- 插件不 `inject` `tools`，不调用 `ctx.tools.register`。
- 模型上下文不因本插件增加任何工具。
- 状态与配置的可见性只存在于设置页（AC-10 的走查范围）。
- 启停动作仅能由人触发，与 DSR-002 的「托管但不自动启动」一致。

## 重访条件

- 出现具体场景：模型必须在作答前知道 codexpro 状态（例如需要判断某能力是否可用）。
- 用户明确要求模型可代为启停，并接受上述安全面变化。
