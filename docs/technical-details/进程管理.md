# 进程管理

## 权威范围

本文唯一拥有 codexpro 进程的启动、状态、健康探测、终止与残留处置语义，以及实现这些语义所依赖的 DSH 能力边界。配置与 profile 写入归 `配置与profile投影.md`；Client↔Host 传输归 `RPC通道与设置页.md`。

## 一、能力边界（已取证）

### 宿主提供的进程能力

`ctx.subprocess` 是 DSH 提供的子进程能力 seam，`bundle/base/cordis.patch.yml` 默认挂载其本地实现。对本设计关键的三条契约（来自服务定义原文）：

1. `spawn(spec)` 返回**同步可用**的句柄。
2. `SubprocessHandle.terminate()` 是「该 seam 唯一的终止动词」，幂等，范围消失后为 no-op；spec 的 abort signal 亦触发它。
3. `waitForExit()` 等待**同一托管范围清空**，不只是被 spawn 的命令报告退出——因此存活的后代仍可被观察。
4. **服务销毁会终止所有仍在运行的托管进程并等待其退出**。

最后一条是本设计选择该 seam 而非裸 `child_process` 的决定性理由（见 §六）。其 Windows 实现经进程容器（Win32 Job）提供整树终止；**该容器在本机可用已实测确认**（见 §五）。

### 环境清洗（必须绕开的陷阱）

`ctx.subprocess` 在把环境交给子进程前，剔除名称匹配 `/KEY|PASSWORD|SECRET|TOKEN/i` 的变量，以及全部 `DSH_*` 变量。

实测对照（复刻该正则逐项判定）：

| 变量 | 是否存活 | 结论 |
|------|----------|------|
| `CODEXPRO_HOME` | 存活 | 可经 env 传递 |
| `CODEXPRO_ROOT` | 存活 | 可经 env 传递 |
| `CODEXPRO_ALLOWED_ROOTS` | 存活 | 可经 env 传递 |
| `CODEXPRO_TUNNEL` | 存活 | 可经 env 传递 |
| `CODEXPRO_PORT` | 存活 | 可经 env 传递 |
| `CODEXPRO_HTTP_TOKEN` | **被剔除** | 命中 `TOKEN`；**必须经其它通道传递** |

**token 的传递方式**：经 codexpro profile 文件的 `token` 字段（见 `配置与profile投影.md`）。codexpro 启动时从 profile 读取既有 token（其 `settings set` 路径即如此），因此无需经 env 传递。这同时满足 C-07（跨启停稳定）。

### 可执行解析（平台敏感，已验证）

| 启动形态 | `shell:false` 结果 |
|----------|--------------------|
| 裸名 `codexpro` | **ENOENT**——Windows 上该名字是 `.cmd` shim，在 argv 不经 shell 解释的语义下无法执行 |
| `node` + `codexpro/scripts/codexpro.mjs` | **成功**（输出版本 `0.30.2`） |

因此 `argv` 形态固定为：

```
argv = [process.execPath, <codexproEntry>, "start", "--root", <anchorDir>, ...]
```

`codexproEntry` 经包解析得到（`createRequire` 解析 `codexpro/package.json`，取其 `bin.codexpro` 指向的真实 `.mjs` 文件），**不硬编码绝对路径**。解析失败时以稳定错误码呈现，**不回落到裸名**。

## 二、启动

### 参数构造

| 参数 | 取值 | 说明 |
|------|------|------|
| `--root` | 锚点目录 | 决定 profile 文件名与默认上下文 |
| `--port` | `Config.port` | |
| `--tunnel` | `Config.tunnelMode` | `none` 时为 `none` |
| `--hostname` | `Config.tunnelHostname` | 仅具名 tunnel 时传入 |
| `--mode` | `agent` | 固定（非目标：不支持 handoff/pro） |
| `--bash` | `Config.bashMode` | |
| `--write` | `Config.writeMode` | |

**不传 `--headless`**：headless 会绕开 codexpro 的非 TTY stdin 控制通道，而该通道是其唯一完整的自身清理路径（实测，见 §五与 DSR-007）。

**不传 `--token`**：token 经 profile 文件传递，避免出现在进程命令行（命令行可被同机进程读取）。

### spawn 规格

| 字段 | 取值 | 理由 |
|------|------|------|
| `argv` | 见上 | 不经 shell 解释 |
| `cwd` | 锚点目录 | codexpro 以 cwd 为上下文基准 |
| `stdio.stdin` | `'pipe'` | **必需**：停止主路径依赖它（见 §五） |
| `stdio.stdout` | collect 模式（有界） | 需读取就绪行与错误输出 |
| `stdio.stderr` | collect 模式（有界） | |
| `graceMs` | `5000` | 终止宽限期 |
| `env` | `{ CODEXPRO_HOME: <dataHome> }` | 数据目录隔离（C-05）；token 不在此处 |

**`CODEXPRO_HOME` 是隔离关键**：它决定 codexpro 的 profile 与 runtime 文件位置。置于 `<$DSH_HOME>/codexpro` 使各 DSH 实例互不可见（C-05）。

### 就绪判定

进程「运行中」的判定**不依赖 stdout 解析**，而是轮询 `GET http://127.0.0.1:<port>/healthz`（见 §三）。理由：stdout 文案可能随 codexpro 版本变化，而健康端点是其自身启动流程使用的判据。

启动失败判定（满足任一）：

- 句柄 `done` 以退出结算（进程提前退出）；
- 就绪轮询在超时内未成功；
- 就绪前输出中出现可识别的错误（如端口占用）。

失败时必须采集并呈现：**退出码、stderr 尾部、就绪期间 stdout 尾部**。

## 三、健康探测

| 项 | 取值 |
|----|------|
| 目标 | `http://127.0.0.1:<port>/healthz` |
| 方法 | `GET` |
| 认证 | `Authorization: Bearer <httpToken>`（token 非空时） |
| 成功判据 | HTTP 2xx 且响应体 `ok === true` |
| 单次超时 | 3–5 秒 |
| 轮询间隔 | 就绪阶段 250 ms；运行期状态刷新按需触发，不做后台高频轮询 |

**只访问回环地址**（S-05）。响应体可用于展示：`authEnabled`、`authRequired`、`connection_diagnostics`（请求计数、最近 MCP 请求时间等），这些是 codexpro 自己暴露的健康数据。

## 四、状态机

```
idle ──start──▶ starting ──healthy──▶ running
  ▲                │                     │
  │                └──fail──▶ failed     │
  │                                │     │
  └──────────stop──────────────────┴─────┘
                      （failed 与 running 均可 stop）
        stopping ──exited──▶ idle
```

| 状态 | 含义 | 可执行动作 |
|------|------|-----------|
| `idle` | 未运行 | start |
| `starting` | 已 spawn，等待健康 | stop（中止启动） |
| `running` | 健康探测通过 | stop、复制 URL |
| `stopping` | 已发起终止，等待范围清空 | 无（防重入） |
| `failed` | 启动失败或运行中异常退出 | start（重试）、stop（清理） |

不变量：

1. `starting`/`stopping` 为**过渡态**，期间拒绝重复触发同一动作（防重入）。
2. 状态只反映**本插件持有的句柄**；不基于 codexpro 的 runtime 文件推断（见 §七）。
3. 进程句柄只由 `adapter/process.js` 持有。

## 五、终止与残留防护

### 停止主路径（已实测定型）

**主路径：向 stdin 写 `q`。**

codexpro 的控制面板在**非 TTY** stdin 下进入一条显式分支：读 stdin，收到 `q` 即执行其 `cleanup()` 后 `exit(0)`。这是唯一能触发 codexpro 自身三步清理的通道：回收 tunnel 子进程、删除 `runtime/<hash>.json`、清理 tunnel 凭据。

实测对照（同一隔离环境，三条路径）：

| 停止方式 | 退出码 | runtime 文件 | 端口 | 残留进程 |
|----------|--------|--------------|------|----------|
| **stdin `q`** | **0** | **已清理** | 释放 | 0 |
| `taskkill /T /F`（树杀） | 1 | 未清理 | 释放 | 0 |
| 父进程被硬杀（模拟崩溃） | — | 残留 | 释放 | 0 |

⇒ 硬杀虽能终止进程树，但不触发清理。因此 `q` 是停止的唯一完整路径。

**为何不使用 `--headless`**：headless 会跳过整个控制面板，从而失去 `q` 通道。其唯一实质收益是打印 `CODEXPRO_READY <url>` 就绪行，而本设计的就绪判定不解析 stdout（用 `/healthz`，见 §三）⇒ 该收益为零。

**为何不依赖信号**：Windows 上外部对 node 进程发送 `SIGTERM`/`SIGINT` 不执行其 JS 处理器（实测：目标进程注册处理器并在其中写标记文件；发信号后进程消失而标记文件未生成）。codexpro 的源码级 `SIGINT`/`SIGTERM` 处理器因此**在实践中不可达**。

**`adapter/process.js` 的 `stop()` 是唯一终止入口**，内部顺序固定为：

1. 向 `stdin` 写 `q`；
2. 等待进程退出，超时取 `graceMs`；
3. 未退出则 `handle.terminate()` + `await handle.waitForExit()`（兜底）。

### 分层防线

| 层 | 触发场景 | 覆盖内容 |
|----|----------|----------|
| stdin `q` | 用户点击停止 | 完整清理（tunnel、runtime、凭据） |
| `terminate()` + `waitForExit()` | `q` 未生效、插件卸载、DSH 退出 | 进程终止（含整树），**不触发 codexpro 自身清理** |
| `ctx.subprocess` 服务销毁 | 插件 fiber 处置、DSH 进程退出 | 终止全部托管进程并等待其退出 |

### 整树终止能力（已实测）

`ctx.subprocess` 在 Windows 上经进程容器（Win32 Job + `KILL_ON_JOB_CLOSE`）捕获后代。实测确认 **本机 `probeWindowsJob()` 判定为真**（`containmentMode = windows-job`），且三层进程树的父与孙同时终止。

**注意**：`dsh-win32-process` 包内无 `.node` 原生文件（绑定经运行时加载），故不能靠「有无原生文件」推断容器可用性。

### 崩溃残留的处置

宿主崩溃（父进程被强杀）时 `runtime/<hash>.json` 会残留。实测该残留中 `pid` 与 `runtimePid` **均已不存活**，因此 codexpro 下次读取时会判定为「未运行」并自行删除该文件。⇒ 插件**不清理**该文件，也不需要「孤儿认领」。

### 防残留的硬规则

1. 停止后必须**实际验证**范围已清空（`waitForExit()` 返回 `true`），不接受「已发起终止」作为成功判据。
2. 插件自身不得在 fiber 处置路径上**等待依赖本 fiber 结算**的在途工作——否则构成自我等待闭环，表现为 DSH 启动静默卡死（仓库既有红线）。`waitForExit()` 等的是子进程 OS 退出，**不依赖本 fiber**，属于允许的等待。
3. 不做「下次启动时清理上次残留」的自动认领：进程容器已覆盖正常与崩溃两条路径；无句柄时杀进程风险高于收益。

## 六、为何用 `ctx.subprocess` 而非裸 `node:child_process`

| 维度 | 裸 `child_process` | `ctx.subprocess` |
|------|--------------------|------------------|
| 插件卸载时清理 | 需自写 disposer | 服务销毁即终止并等待 |
| DSH 进程退出时清理 | 无 | 服务实现挂 `process` 退出监听做同步强杀 |
| Windows 整树终止 | 无 | 经进程容器（Job）捕获后代（**本机已实测可用**，见 §五） |
| 环境安全 | 全量继承 | 自动剔除凭证形状变量 |

代价是必须显式给出 `stdio`/`cwd`/`graceMs`（该 seam 不提供默认值），且环境被清洗（见 §一，已针对性处理 token 传递）。

## 七、已运行实例的识别边界

codexpro 自身会写 `runtime/<profileId>.json`，其中 `pid` 是 CLI 父进程、`runtimePid` 是 server 子进程。

**本插件不使用它判断进程状态**，理由：

- 该文件只在正常清理路径被删除；父进程被硬杀时会残留（实测确认），据此判断可能误报。
- 该文件同时记录 `pid`（CLI 父进程）与 `runtimePid`（server 子进程），但**不记录 tunnel 进程**，无法据其判断隧道是否仍在。
- 无法处理「终端手工启动的 codexpro」与插件管理的实例并存。

**采用的行为**：状态只反映插件自身句柄。若启动时端口被占，以端口冲突错误呈现（codexpro 自身亦如此，且不会自动换端口），由用户处置。**不做孤儿认领**（§五规则 3）。

## 八、失败语义

| 失败 | 呈现 | 后续 |
|------|------|------|
| 可执行解析失败 | 稳定错误码 + 说明（codexpro 未安装或包结构变化） | 不 spawn；提示安装 `codexpro@>=0.20` |
| 端口被占 | codexpro 的错误文本（含其给出的端口建议） | 用户改端口后重试 |
| 配置校验失败 | 具体字段与原因 | 不 spawn |
| 授权根不存在 | 指出被剔除的路径 | 该路径不写入；其余正常 |
| 就绪超时 | 退出码 + stderr 尾部 | 状态置 `failed` |
| 运行中异常退出 | 退出码 + 信号 + stderr 尾部 | 状态置 `failed` |
| token 缺失 | 自动生成并写入 profile | 继续启动 |
